# Synchronized, Locks, Volatile & Memory Model Basics

## Synchronized

`synchronized` provides mutual exclusion: only one thread at a time can execute a synchronized block guarded by the same monitor. It also makes changes visible to threads that later acquire that monitor.

Example:

```java
class PaymentService {

    private PaymentGateway paymentGateway;
    private int paymentCount = 0;

    public PaymentService(PaymentGateway paymentGateway) {
        this.paymentGateway = paymentGateway;
    }

    public boolean makePayment(float amount) {
        paymentGateway.pay(amount);
        synchronized (this) {
            paymentCount++;
        }

        return true;
    }
}
```

## Locks

An explicit lock, such as `ReentrantLock`, controls access to a critical section. A thread must acquire the lock before entering, and another thread using the same lock must wait until it is released. Unlike `synchronized`, a `Lock` must be released explicitly, usually in a `finally` block.

`tryLock()` attempts to acquire a lock immediately. It returns `false` instead of waiting if another thread holds the lock.

```java
import java.util.concurrent.locks.Lock;
import java.util.concurrent.locks.ReentrantLock;

class SharedCounter {
    private final Lock lock = new ReentrantLock();
    private int count;

    public boolean tryIncrement() {
        if (!lock.tryLock()) {
            return false;
        }

        try {
            count++;
            return true;
        } finally {
            lock.unlock();
        }
    }
}
```

If `tryIncrement()` returns `false`, the caller can skip the operation, retry later, or handle the busy state. The `finally` block ensures the lock is released after a successful acquisition.

## Volatile

`volatile` makes a variable's latest write visible to other threads that read it. It does not provide mutual exclusion or make compound operations (such as `rateLimit--`) atomic.

For example, a volatile value is suitable when threads independently read or replace a configuration value:

```java
class RateLimitConfig {
    private volatile int rateLimit;

    public RateLimitConfig(int rateLimit) {
        this.rateLimit = rateLimit;
    }

    public boolean isWithinLimit() {
        return rateLimit > 0;
    }

    public void updateRateLimit(int count) {
        rateLimit = count;
    }
}
```

If multiple threads need to decrement a shared limit safely, use synchronization or an atomic type such as `AtomicInteger` instead of relying on `volatile`.

### AtomicInteger Example: Token Bucket Rate Limiter

This limiter starts with a full bucket. Each accepted request consumes one token, and a scheduled task can periodically add tokens back up to the bucket's capacity.

```java
import java.util.concurrent.atomic.AtomicInteger;

class TokenBucketRateLimiter {
    private final int capacity;
    private final AtomicInteger tokens;

    public TokenBucketRateLimiter(int capacity) {
        if (capacity <= 0) {
            throw new IllegalArgumentException("capacity must be positive");
        }
        this.capacity = capacity;
        this.tokens = new AtomicInteger(capacity);
    }

    public boolean tryAcquire() {
        int current = tokens.get();

        while (current > 0) {
            if (tokens.compareAndSet(current, current - 1)) {
                return true;
            }
            current = tokens.get();
        }

        return false;
    }

    public void refill(int tokensToAdd) {
        if (tokensToAdd <= 0) {
            throw new IllegalArgumentException("tokensToAdd must be positive");
        }

        tokens.updateAndGet(current ->
                (int) Math.min(capacity, (long) current + tokensToAdd));
    }
}
```

For example, with a capacity of 10, call `refill(10)` once per second. `tryAcquire()` returns `true` when a request consumes a token and `false` when the bucket is empty. The compare-and-set loop makes checking and consuming a token atomic when multiple request threads call it concurrently.

This limiter is local to one application instance. Multiple replicas each have their own bucket; a distributed rate limit needs shared coordination.

## Memory Models Basics

The Java Memory Model (JMM) defines how threads interact through shared memory. It specifies when one thread's writes are visible to another thread and what ordering guarantees exist. It is a set of rules for Java programs, not a diagram of physical memory or CPU caches.

The JMM provides **visibility**, **ordering**, and **atomicity** guarantees through mechanisms such as `volatile`, `synchronized`, locks, and atomic classes. Without proper coordination, threads may observe stale values or interleave operations in unexpected ways.

For example, when one thread writes `data` and then sets the volatile `ready` flag, a thread that reads `ready` as `true` is guaranteed to see the earlier write to `data`:

```java
class Message {
    private int data;
    private volatile boolean ready;

    public void publish() {
        data = 42;
        ready = true;
    }

    public void consume() {
        if (ready) {
            System.out.println(data); // prints 42 if ready is true
        }
    }
}
```

Similarly, when one thread releases a monitor or lock and another thread later acquires that same monitor or lock, the second thread sees changes made before the release. These ordering and visibility relationships are called **happens-before** guarantees.
