# SOLID Principles

SOLID stands for five principles for designing maintainable object-oriented software.

## Single Responsibility Principle

A class should have one reason to change.

```java
interface PaymentMethod {
    boolean doPayment();
}

class Payment {
    private final PaymentMethod paymentMethod;

    public Payment(PaymentMethod paymentMethod) {
        this.paymentMethod = paymentMethod;
    }

    public boolean performPayment() {
        return paymentMethod.doPayment();
    }
}
```

## Open/Closed Principle

Software entities should be open for extension but closed for modification.

```java
class CreditCard implements PaymentMethod {
    @Override
    public boolean doPayment() {
        System.out.println("Payment made using credit card");
        return true;
    }
}

class NetBanking implements PaymentMethod {
    @Override
    public boolean doPayment() {
        System.out.println("Payment made using net banking");
        return true;
    }
}
```

## Liskov Substitution Principle

Subclasses should be replaceable for their parent classes without breaking the expected behavior of the program.

```java
class Manager {
    public void managePayment(PaymentMethod paymentMethod) {
        Payment payment = new Payment(paymentMethod);
        payment.performPayment();
    }

    public void example() {
        CreditCard card = new CreditCard();
        NetBanking netBanking = new NetBanking();

        managePayment(card);
        managePayment(netBanking);
    }
}
```

## Composition over inheritance

Prefer composing objects to extending classes when possible. Composition represents a "has-a" relationship, while inheritance represents an "is-a" relationship. Composition usually provides more flexibility because behavior can be changed by supplying a different dependency.

```java
interface Engine {
    void start();
}

class Car {
    private final Engine engine;

    public Car(Engine engine) {
        this.engine = engine;
    }

    public void startCar() {
        engine.start();
    }
}
```

## Interface Segregation Principle

Classes should not be forced to depend on methods they do not need. Prefer small, focused interfaces over large ones.

```java
interface Printer {
    void print();
}

interface Scanner {
    void scan();
}

class SimplePrinter implements Printer {
    @Override
    public void print() {
        System.out.println("Printing document");
    }
}

class MultiFunctionPrinter implements Printer, Scanner {
    @Override
    public void print() {
        System.out.println("Printing document");
    }

    @Override
    public void scan() {
        System.out.println("Scanning document");
    }
}
```

## Dependency Inversion Principle

High-level and low-level modules should depend on abstractions, not directly on each other.

```java
interface PaymentGateway {
    boolean pay(double amount);
}

class StripePaymentGateway implements PaymentGateway {
    @Override
    public boolean pay(double amount) {
        System.out.println("Paid using Stripe");
        return true;
    }
}

class PaymentService {
    private final PaymentGateway paymentGateway;

    public PaymentService(PaymentGateway paymentGateway) {
        this.paymentGateway = paymentGateway;
    }

    public boolean makePayment(double amount) {
        return paymentGateway.pay(amount);
    }
}
```
