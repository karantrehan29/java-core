# ExecutorService, Thread Pools, Future, CompletableFuture

## Why use an executor?

Creating a new `Thread` for every task adds overhead and makes it difficult to control how many tasks run at once. The executor framework separates **submitting a task** from **the thread that runs it**:

- A task describes work (`Runnable` or `Callable<T>`).
- An executor decides when and on which worker thread to run it.
- A `Future` represents the result or completion of submitted work.

Tasks submitted to an executor should not assume they will run on a particular thread or in a particular order unless the executor and the task coordination explicitly provide that guarantee.

## `Executor` and `ExecutorService`

`Executor` is a small interface with `execute(Runnable)`. `ExecutorService` extends it with task-submission methods, lifecycle management, and APIs for waiting on groups of tasks.

`ExecutorService` is an interface; it does not itself promise to use a thread pool. Implementations such as those returned by `Executors` commonly use worker threads, while other implementations can have different execution strategies.

### Submitting tasks

- `execute(Runnable)` submits work but does not return a `Future`.
- `submit(Runnable)` returns a `Future<?>`. Its result is `null` when the task completes normally.
- `submit(Callable<T>)` returns a `Future<T>` for the value produced by `call()`.
- `Callable<T>` can return a value and throw checked exceptions; `Runnable.run()` cannot return a value or declare checked exceptions.

```java
ExecutorService executor = Executors.newFixedThreadPool(2);

executor.execute(() -> System.out.println("Fire-and-forget task"));

Future<?> runnableFuture = executor.submit(() -> System.out.println("Runnable task"));
Future<Integer> callableFuture = executor.submit(() -> 20 + 22);

Integer answer = callableFuture.get(); // waits for completion; answer is 42
```

`Future.get()` blocks until the task completes. It can throw:

- `InterruptedException` if the waiting thread is interrupted.
- `ExecutionException` if the task failed; inspect `getCause()` for the original exception.

Use `isDone()` to check completion without waiting and `cancel(true)` to request cancellation. Cancellation is cooperative: interruptible tasks should respond to interruption, and a task that ignores interruption may continue running. `get()` after successful cancellation throws `CancellationException`.

If interrupted while waiting, generally restore the interrupt status after handling the interruption:

```java
try {
    result = future.get();
} catch (InterruptedException e) {
    Thread.currentThread().interrupt();
    throw new IllegalStateException("Waiting for task was interrupted", e);
} catch (ExecutionException e) {
    throw new IllegalStateException("Task failed", e.getCause());
}
```

### Waiting for multiple tasks

- `invokeAll(tasks)` submits all tasks and returns their futures after all have completed (or the call is interrupted/times out).
- `invokeAny(tasks)` returns the result of one successfully completed task; it may cancel unfinished tasks after a result is available.

These methods are useful when a group of independent tasks should be submitted and collected together.

## Thread pools

A thread pool reuses worker threads to run multiple tasks. Reuse avoids creating a new thread for every task and lets an application limit or otherwise manage concurrent work.

Common factory methods include:

- `Executors.newFixedThreadPool(n)`: uses a fixed number of workers. Useful for limiting active threads, but its queue is unbounded, so overload can cause queued tasks and memory use to grow.
- `Executors.newSingleThreadExecutor()`: runs tasks sequentially on one worker; tasks are not run concurrently.
- `Executors.newCachedThreadPool()`: creates workers as needed and reuses idle ones. It can create many threads under load, so it is not automatically a safe choice for unbounded workloads.
- `Executors.newScheduledThreadPool(n)`: schedules delayed or recurring tasks; it returns a `ScheduledExecutorService`.
- `Executors.newWorkStealingPool()`: uses work-stealing workers and is suited to many small, independent tasks. It does not guarantee submission order.

Choose a pool based on the workload and how it should handle overload—not just the factory method's name. For production services that need explicit queue limits, rejection behavior, or thread naming, `ThreadPoolExecutor` provides more control. Avoid submitting an unbounded volume of tasks to an executor with an unbounded queue.

For blocking I/O, a large pool can be useful, but a thread pool is not a substitute for limiting downstream requests or applying backpressure. For CPU-bound work, a pool near the number of available processors is a common starting point, not a universal rule.

### Scheduling is separate

`ExecutorService` does not generally mean “run this at a particular time.” Use `ScheduledExecutorService` for one-shot delayed or periodic execution:

```java
ScheduledExecutorService scheduler = Executors.newScheduledThreadPool(1);
scheduler.schedule(() -> System.out.println("Runs after a delay"),
        1, TimeUnit.SECONDS);
```

`scheduleAtFixedRate` targets a regular cadence, while `scheduleWithFixedDelay` waits for the previous run to finish and then waits the requested delay before the next run. Periodic tasks should handle their own failures: an uncaught exception can prevent later executions of that periodic task.

## Executor lifecycle

An executor must be shut down when it is no longer needed. Otherwise, its worker threads may keep the application alive.

- `shutdown()` stops accepting new tasks and lets already-submitted tasks finish.
- `shutdownNow()` attempts to interrupt active tasks and returns tasks that never started; it does not guarantee that running tasks stop.
- `awaitTermination(timeout, unit)` waits for termination for a limited time.

Example with graceful shutdown and a bounded wait:

```java
ExecutorService executor = Executors.newFixedThreadPool(2);
try {
    Future<Integer> result = executor.submit(() -> 6 * 7);
    System.out.println(result.get());
} finally {
    executor.shutdown();
    try {
        if (!executor.awaitTermination(5, TimeUnit.SECONDS)) {
            executor.shutdownNow();
        }
    } catch (InterruptedException e) {
        executor.shutdownNow();
        Thread.currentThread().interrupt();
    }
}
```

## `Future`

A `Future<T>` is a handle to the outcome of an asynchronous computation. It supports:

- `get()`: wait for and retrieve the result.
- `get(timeout, unit)`: wait up to a time limit.
- `isDone()`: check whether the task completed, failed, or was cancelled.
- `isCancelled()`: check whether it was cancelled.
- `cancel(mayInterruptIfRunning)`: request cancellation.

`Future` is useful for tracking one submitted task, but it does not provide convenient composition. For example, waiting on several futures manually can lead to blocking and complicated error handling. `CompletableFuture` provides a way to build dependent asynchronous stages.

## `CompletableFuture`

`CompletableFuture<T>` implements both `Future<T>` and `CompletionStage<T>`. It can be completed by a task or explicitly, and its stages can be chained to transform results, combine work, or handle failures without manually calling `get()` between each step.

### Creating and transforming a pipeline

- `supplyAsync(Supplier<T>)` runs work that produces a value.
- `runAsync(Runnable)` runs work without producing a value.
- `thenApply(...)` transforms a result synchronously in a completion thread.
- `thenAccept(...)` consumes a result without returning another value.
- `thenRun(...)` runs an action without using the previous result.

```java
CompletableFuture<Integer> answer =
        CompletableFuture.supplyAsync(() -> 20)
                .thenApply(value -> value * 2);

answer.thenAccept(value -> System.out.println("Answer: " + value));
```

Without an explicit executor, the `*Async` methods typically use the common `ForkJoinPool`. Non-async stages such as `thenApply` may run on the thread that completes the previous stage. Use the overloads that accept an `Executor` when you need to choose where asynchronous work runs.

### Chaining asynchronous work

- `thenCompose(...)` chains a function that itself returns a `CompletionStage`, flattening the nested asynchronous result. Use it when the next operation is asynchronous and depends on the previous result.
- `thenCombine(...)` combines the results of two independent stages after both complete.

```java
CompletableFuture<String> userName =
        CompletableFuture.supplyAsync(() -> "Avery");

CompletableFuture<String> greeting =
        userName.thenCompose(name ->
                CompletableFuture.supplyAsync(() -> "Hello, " + name));

CompletableFuture<Integer> price = CompletableFuture.supplyAsync(() -> 12);
CompletableFuture<Integer> tax = CompletableFuture.supplyAsync(() -> 2);
CompletableFuture<Integer> total = price.thenCombine(tax, Integer::sum);
```

Use `thenApply` for a synchronous transformation that returns a value; use `thenCompose` when the transformation starts another asynchronous operation.

### Handling errors

- `exceptionally(...)` provides a fallback value if the stage failed.
- `handle(...)` receives either the result or the failure and can produce a replacement result.
- `whenComplete(...)` observes the result or failure, usually for logging or cleanup, without normally changing the outcome.

```java
CompletableFuture<String> message =
        CompletableFuture.supplyAsync(() -> {
            throw new IllegalStateException("Request failed");
        }).exceptionally(error -> "Fallback: " + error.getMessage());
```

Exception-handling stages affect the stages that follow them. Decide whether a fallback is valid for the application; do not hide failures with a success-looking default when the failure should be reported.

### Waiting for several stages

`CompletableFuture.allOf(...)` completes when every supplied future completes. It returns `CompletableFuture<Void>`, so retrieve individual results from the original futures after `allOf` completes. `anyOf(...)` completes when any supplied future completes and returns a general `Object`.

Calling `join()` waits like `get()`, but reports failure using unchecked `CompletionException` rather than the checked `ExecutionException`. Prefer composing stages when possible; blocking with `get()` or `join()` inside another asynchronous task can tie up worker threads and reduce throughput.

## Complete example

This Java 8+ example submits a `Callable`, reads its `Future`, and runs a `CompletableFuture` pipeline using an explicit executor:

```java
import java.util.concurrent.CompletableFuture;
import java.util.concurrent.ExecutionException;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.Future;

public class ExecutorServiceExample {
    public static void main(String[] args)
            throws InterruptedException, ExecutionException {
        ExecutorService executor = Executors.newFixedThreadPool(2);

        try {
            Future<Integer> future = executor.submit(() -> 20 + 22);
            System.out.println("Future result: " + future.get());

            CompletableFuture<Integer> pipeline =
                    CompletableFuture.supplyAsync(() -> 10, executor)
                            .thenApply(value -> value * 3);

            System.out.println("CompletableFuture result: " + pipeline.get());
        } finally {
            executor.shutdown();
        }
    }
}
```

Expected output:

```text
Future result: 42
CompletableFuture result: 30
```

## Common pitfalls

- Forgetting `shutdown()` can leave executor threads running after the work is done.
- Calling `get()` immediately after every submission makes asynchronous code behave sequentially.
- Assuming cancellation forcibly stops a task; interruption must be handled cooperatively.
- Using an unbounded task queue or creating too many threads can exhaust memory or other resources.
- Sharing mutable state between tasks without synchronization or another safe coordination mechanism causes race conditions.
- Blocking a pool's worker threads while waiting for work that needs the same exhausted pool can cause stalls or deadlock.
- Assuming task submission order guarantees task start or completion order; this depends on the executor and task coordination.
- Swallowing exceptions from `Future` or `CompletableFuture` makes task failures difficult to diagnose.

## Quick comparison

| API | Main purpose | Result handling |
| --- | --- | --- |
| `ExecutorService` | Submit tasks and manage their execution/lifecycle | Submit returns a `Future` |
| `Future<T>` | Track or cancel one task and retrieve its result | `get()` blocks |
| `CompletableFuture<T>` | Compose asynchronous stages and handle completion | Chain stages; `get()`/`join()` can still block |
| `ScheduledExecutorService` | Run work after a delay or periodically | Scheduled task returns a `ScheduledFuture` |
